## 一般原則
* 暗黙のうちに推測するのではなく、前提条件を明確にする: 些細な推測であればそのまま進め、後戻りが困難な選択や確信が持てない場合は立ち止まって質問すること。計画段階で早めに、まとめて質問を行う。
* Git/GitHubへの書き込み（commit / push / PR / comment）: /code-flow:* スキルを使用し、生の git add/commit/push や gh pr create は絶対に使用しないこと。読み込みの場合は、gh CLI または git を直接使用する。
* コミットには署名（サイン）を行うこと。

## 開発ワークフロー

* cmux内でセッションを開始した場合は、作業内容が一目で分かる短い名前を決め、`cmux rename-workspace "{sessionを表す名前}"` を実行すること。
* herdr内でセッションを開始した場合は、作業内容が一目で分かる短い名前を決め、`herdr pane current --current` で workspace_id を取得したうえで `herdr workspace report-metadata <workspace_id> --source claude:session-name --token summary="{sessionを表す名前}"` を実行すること。
* コードベースを変更する場合には、`git worktree`を用いること。同一リポジトリを複数のセッションで並列に作業することがあるためです。
* 1つのチケット: インラインで実行する。大規模 / 複数チケット: インラインではなく、別のセッションやワークツリーを使用する（仕組みは「委譲」の項目を参照）。
* 基本的な自律性 (Standing autonomy): L2（PRまでは自律的、マージは人間が判断するゲート）。L3の場合は開始時に明示的な確認が必要となる。
* PR / マージゲートでの対応（ループ内またはループ外）:
  * PRの本文は**最小限**にすること。「何を・なぜ」を数行、あとは diff / CI / plan で読み取れないことだけ書く。差分の言い換え・自明な項目・網羅的なチェックリストは書かない。自動QAで拾えない検証（UI/UX・外部連携・実データ影響など）が必要な場合に**限って**、確認手順を追記する。
  * QA後: 結果を1つの固定（sticky）PRコメントとして投稿すること（隠しマーカーを使用してその場で更新し、実行のたびに新しいコメントを積み重ねないこと）。
* レビュー対応した時には、その変更によって新たな問題・不整合が起きていないかを検査すること。

## 委譲と並列処理 (Delegation & Parallelism)

* **コンテキストを大量に消費する作業（広範な検索、複数ファイルの読み込み、長いログなど）:** サブエージェントにオフロードし、その要約のみを保持すること（これにより、後のメイン処理が軽量に保たれる）。そのサブエージェントが独自のエージェントを生成してもよい（ネストは浅く保つこと）。些細なタスクは委譲しないこと（システムプロンプトのオーバーヘッドが節約効果を上回ってしまうため）。
* **N個の独立したイシュー:** `/bunshin:run` を使用する（dev-loopはバッチ並列モードをこれに委譲する）。
* **次のタスクへの移行（現在のタスク完了後）:** 簡単な引き継ぎ用の要約（現在の状態 + 次のタスク）を作成し、新しいセッションで開始すること：`iTerm Split Vertically` + `claude -w <name>`（組み込みの新規gitワークツリー）。

## 言語

* 会話のデフォルトは**日本語**とする。ユーザーが英語で入力した場合は英語に切り替えること。
* リポジトリに書き込まれるもの（コード、コメント、ドキュメント、PR、コミット）について：既存の類似ファイルの言語の慣習に合わせること。明確な前例がない場合は英語をデフォルトとする。

## CLAUDE.md のメンテナンス 

* Claudeが規則やコマンドを2回間違えた場合は、該当するセクションに簡潔な命令型のルールを追加すること。約3ヶ月ごとに各ルールの存在理由を再評価し（「これを削除したら間違いが起こるか？」）、問題がないものは削除する。
* 文章による指示よりも仕組み化を優先すること（プロンプトよりも枠組みを重視）：繰り返されるワークフロー（2回以上） → `/skill-creator:skill-creator`、トリガーされる動作 → フック / ゲート、権限・環境変数 → 設定ファイル（settings）。適切な仕組みがない場合にのみ、`CLAUDE.md`にルールを記述する。
* 目安として、100行以下 / 2.5kトークン以下を目標とすること。Claude Codeのデフォルトを信頼し、実際に観察された間違いによって必要となったものだけをカスタマイズすること。
